# Audit — September 2026

Full read of the repo, the release pipeline and the surrounding services. Findings are
ordered by **how much they slow down or endanger future work**, not by how bad they look.

Legend — **Impact**: what it costs us. **Effort**: S < 1 day, M 1–3 days, L > 3 days.

## P0 — fix before the next feature lands

### A1. ✅ DONE (2026-09-10) — repository was 388 MB because binaries are committed
**Result: 388 MB → 58 MB on a fresh clone, all 138 commits preserved.** yt-dlp is now pinned
in `clipagent/src-tauri/tools.lock`, fetched by `scripts/fetch-yt-dlp.sh` and verified
against the checksums yt-dlp publishes for that release; the weekly workflow edits one line
instead of committing 37 MB. History rewritten with `git filter-repo`; `main`, 27 tags and
all branches force-pushed. Pre-rewrite mirror kept at `~/dev/klipprr-backup-20260910-142600`.
**Remaining:** ffmpeg + ffprobe are still committed (~150 MB, added once, never change).
Moving them out needs somewhere to host them — see A5.

<details><summary>Original finding</summary>

**Impact:** every clone, every CI checkout, every agent session pays for it. The weekly
yt-dlp workflow commits a fresh 37 MB binary, so the repo grows ~37 MB/week *forever* —
10 bumps so far, ~350 MB of the 388 MB total. **Effort:** M

76.2 MB  clipagent/src-tauri/bin/ffprobe
75.2 MB  clipagent/src-tauri/bin/ffmpeg

**Fix:** stop committing binaries. Fetch them at build time, pinned by version + SHA256

`bin/versions.lock` file. Then rewrite history with `git filter-repo` to drop the blobs.

**This is destructive and coordinated** — it rewrites every commit hash, so every clone
must be re-cloned. Needs a founder go-ahead and a moment when nothing is in flight.

### A2. ✅ DONE (2026-09-10) — build output was committed to git
**Impact:** `clipagent/ui/out/` is tracked, so a one-line UI change produces a 20+ file
diff of minified JS, hashed fonts and Next.js manifests. Code review of UI changes is
effectively impossible, and merge conflicts in generated files are guaranteed. **Effort:** S

**Fix:** gitignore `clipagent/ui/out/`, build it in CI (already happens — the committed
copy is redundant), and keep it locally for dev builds.

### A3. Zero tests, on a product whose promise is precision
**Impact:** every change is verified by hand or not at all. The resolve format-selection
logic — the most fragile, most business-critical code in the app — has no regression
safety net, and yt-dlp's output changes upstream constantly. **Effort:** M

**Fix, in priority order:**
1. Rust unit tests over **recorded yt-dlp JSON fixtures** for `resolve.rs` selection:
   muxed-present, muxed-absent, AV1-only-at-4K, HLS-only, audio-only. This is high value
   and cheap — the logic is pure once the JSON is in hand.
2. A cut-accuracy integration test: generate a synthetic clip with burned-in frame numbers,
   export a known range, assert the first and last frame numbers.
3. Playwright smoke test of the UI against a stubbed agent.

### A4. ✅ DONE (2026-09-10) — three competing definitions of "what a plan can do", two of them dead
**Impact:** `plan.ts` defines a `Plan` type and a `PLAN_CAPABILITIES` map covering only
`free` and `pro`. `usage.ts` defines `PaidPlanKey` covering `free|pro|max`. `license.rs`
defines `Plan` covering all three and is the **only one that actually runs** — capabilities
reach the UI through `/capabilities`, which calls `capabilities_for_plan()` in Rust, and
that handles `max` correctly. **Effort:** S

So this is not currently a live billing bug — verified: a Max licence gets full
capabilities. It is a **trap**. The next person to add a gated feature has a 2-in-3 chance
of reaching for the dead TypeScript map, which is missing a tier and wired to nothing, and
shipping a real version of the bug this entry originally claimed.

`plan.ts` and `license.ts` (a `verifyLicense` helper) have **zero importers**.
`capabilities.ts` is imported for its type only.

**Fix:** delete `plan.ts` and `license.ts`; keep `capabilities.ts` as the shared type;
document Rust `capabilities_for_plan()` as the single source of truth.

### A5. We ship Intel binaries inside an Apple-Silicon-only app
**Impact:** the release builds `--target aarch64-apple-darwin` only, but the bundled
`ffmpeg` and `ffprobe` are **x86_64**. Every export and every PCM preview fix therefore
runs under Rosetta 2 translation — and on a Mac where Rosetta is not installed, they
**cannot execute at all**. macOS only offers to install Rosetta when the user launches a
GUI app, not when an already-running app spawns an x86 subprocess, so the failure surfaces
as an opaque export error on a machine that otherwise works. **Effort:** M

Measured on this machine (30 s 1080p source, same command line):

| Path | x86_64 (Rosetta) | arm64 native |
|---|---|---|
| Hardware encode (`h264_videotoolbox`) — what exports use | 2.35 s | 2.32 s |
| Software encode (`libx264`) | 1.07 s | 0.60 s |

So the honest performance story is narrow: exports are hardware-encoded on macOS and barely
care. **The real risk is the hard dependency on Rosetta being installed**, plus ~44% on any
software path.

Also: the two binaries are from **different builds** — `ffmpeg 6.1.1` (release, 2023) and
`ffprobe N-122942` (nightly, 2026). Probing with one version and encoding with another is
how you get bugs nobody can reproduce.

**Trap found while testing a replacement:** the app passes `-prio_speed` and
`-power_efficient` to `h264_videotoolbox`. `-power_efficient` only exists from ffmpeg 6.1.
A 6.0 build fails the whole encode with `Error splitting the argument list: Option not
found`. **Whatever binaries we bundle, the encoder arguments must be built from a
capability probe** (`ffmpeg -h encoder=h264_videotoolbox`) rather than hard-coded, or the
next binary swap silently breaks every macOS export.

**Open decision — where arm64 macOS ffmpeg comes from.** There is no official static
macOS build. Candidates: `eugeneware/ffmpeg-static` (pinnable by tag + checksum, but its
`b6.1.1` tag actually contains **6.0** — too old), osxexperts.net (current arm64 builds,
versioned filenames, personal site), or building it ourselves in CI (full control,
reproducible, ~30 min per release).

## P1 — actively slowing development

### B1. `page.tsx` is 2,275 lines; `ExportPanel.tsx` is 979
**Impact:** nearly all state lives in one component. Any two changes collide. Effect
dependencies are `eslint-disable`d in several places because the real dependency graph is
unmanageable, which is how stale-state bugs get in. **Effort:** L

**Fix:** extract by domain, not by size — `useResolve`, `usePreviewSource`, `useClips`,
`useExport` hooks; a small reducer for editor state. Do it *while* doing the UI rebrand,
not as a separate refactor nobody will fund.

### B2. `clipagent/ui/` is a fossil
**Impact:** contains a vestigial `package.json`, `next.config.ts`, empty `app/` and
`components/` dirs (only `.DS_Store` inside), a committed `.next/dev` cache, and 436 MB of
unused `node_modules`. New contributors reasonably assume it is a real project. **Effort:** S

**Fix:** reduce to the `out/` drop folder, or better — have `copy-out.js` write into
`clipagent/src-tauri/frontend/` and delete `clipagent/ui/` entirely.

### B3. Duplicated CI (~80 lines) and unpinned Windows dependencies
**Impact:** `release-windows` and `release-windows-only` differ only in trigger and tag
derivation. Both fetch ffmpeg and yt-dlp from `latest` at build time, so the same tag can
produce different binaries on a rebuild. **Effort:** S

**Fix:** one reusable workflow with inputs; pin the fetched versions with checksums.

### B4. Two analytics systems
**Impact:** `analytics.ts` POSTs to `klipprr-web/api/track` **and** PostHog is initialised
separately. Two event vocabularies, two places to look, neither complete. **Effort:** S

**Fix:** pick PostHog (it already carries feature flags and A/B), route everything through
it, keep `/api/track` only if it feeds something Stripe-side that PostHog cannot.

### B5. ✅ DONE (2026-09-10) — `/download-all` blocked a tokio worker for the whole export
**Impact:** `/resolve` was moved to `spawn_blocking`; `/download-all` was not. A long export
can starve the executor and make the UI's `/ping` and preview range reads stall. **Effort:** S

### B6. ✅ DONE (2026-09-10) — junk tracked in git
`cliptool/next` (0 bytes), `cliptool/cliptool@0.1.0` (0 bytes) — shell redirection
accidents. `.DS_Store` files throughout despite being gitignored (they were committed
before the ignore existed). A broken `cliptool/.git/objects` directory with no HEAD.
**Effort:** S

## P2 — worth doing, not urgent

- **B7.** No PR CI at all — no lint, no typecheck, no build check. Only the release workflow
  runs. A broken `main` is only discovered at tag time. **Effort:** S
- **B8.** Version bumping is manual across two files with nothing validating tag agreement.
  **Effort:** S
- **B9.** `paths.rs` has two unused imports behind `cfg(windows)` that warn on every build.
  Warnings train people to ignore warnings. **Effort:** S
- **B10.** `~/dev/klipprr copy` — a manual folder backup sitting next to the real repo. It
  will eventually be edited by mistake. Delete it; git is the backup. **Effort:** S
- **B11.** `/preview-stream` has no caching layer, which is the direct cause of slow
  scrubbing on direct-URL sources. Tracked as a product issue in `FOUNDER-REQUESTS.md` #2.
- **B12.** Export "Original" mode is mislabeled "AV1 – Original" with a warning that it may
  not play — see `PIPELINES.md`. It is a labelling bug that reads as a product defect.

## What is genuinely well built

Say this out loud, because a rewrite instinct is the biggest risk to a working product:

- **Offline license verification with ed25519, private key only on the server.** Correct
  design. Compromising the app does not let anyone mint licences.
- **Reserve-then-refund quota accounting.** A crashed export does not burn the user's quota.
- **The local HTTP server with real Range support.** The right answer for seekable
  `<video>` in a webview, and it is implemented properly (206, Content-Range, clamping).
- **SSRF guard on `/preview-stream`.** Someone thought about it.
- **Signing bundled binaries individually with the right entitlements for PyInstaller
  yt-dlp.** This is fiddly and it is done correctly.
- **The tiered preview swap that preserves playhead position.** Good instinct, and the
  right pattern to build the preview redesign on.

The architecture is sound. The problems are hygiene, test coverage and one weak subsystem
(preview delivery). This does not need a rewrite.
